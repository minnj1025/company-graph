# 공시 기반 기업 관계 그래프

금융감독원 전자공시(DART)에서 **기업과 기업의 관계**, 그리고 **기업이 무엇을 하는지**(사업 내용과 제품)를 뽑아 시점이 붙은 DB로 만들고, 화면과 Agent로 조회한다.
"현대모비스에 납품 계약을 공시한 회사는?", "이 계약은 작년 말 시점에 어떻게 알려져 있었나?", "전기차 배터리 분리막을 만드는 회사는?" 같은 질문에 근거 공시와 함께 답하는 것이 목표다.

개인 프로젝트이고 이름은 임시다. 설계와 진행 기록은 [DESIGN.md](DESIGN.md), 참고한 문헌·사례는 [docs/landscape.md](docs/landscape.md)에 있다.

## 지금 들어 있는 것 (2026-10-09)

상장사 2,759곳(유가증권·코스닥·코넥스)의 공시를 읽었다. 기업 원장은 계열회사 표에 나온 비상장사까지 14,514곳이다.

| 관계 | 출처 | 방법 | 줄 수 (그중 지금 유효) |
|---|---|---|---|
| 계열 | 사업보고서의 계열회사 현황 표 (2023~2025 사업연도) | 양식 파싱 | 177,058 |
| 지분 | 사업보고서의 타법인 출자현황, 최대주주 현황 | OpenDART API + 양식 파싱 | 127,144 |
| 공급계약 | 단일판매ㆍ공급계약 체결 공시 (2024-01 이후) | 양식 파싱 | 12,081 (6,957) |
| 공급계약 해지 | 단일판매ㆍ공급계약 해지 공시 | 양식 파싱 | 244 |
| 지분 취득 결정 | 타법인 주식 및 출자증권 취득결정 공시 | 양식 파싱 | 2,478 (1,570) |
| 지분 처분 결정 | 타법인 주식 및 출자증권 처분결정 공시 | 양식 파싱 | 810 (389) |

읽은 공시는 사업보고서 7,865건, 공급계약 공시 12,333건, 취득·처분 결정 3,183건, 반기보고서 2,587건이다. 관계 추출에 LLM은 쓰지 않았다. 양식이 정해진 공시만 다뤘기 때문이다.

관계 말고 **기업이 무엇을 하는지**도 두 층으로 담았다.

| 층 | 출처 | 방법 | 담은 것 |
|---|---|---|---|
| 사업 내용 | 2025 사업보고서와 2026 반기보고서의 "II. 사업의 내용" | 소제목 단위로 자르기만 한다. 요약하거나 값을 뽑지 않는다 | 보고서 5,314건, 2,751곳, 31,755절 |
| 제품 | 그 안의 "주요 제품 및 서비스" 매출 비중 표 | 표 읽기는 규칙, 이름과 제품군 붙이기는 LLM | 1,793곳, 15,802줄 |

- **사업 내용**은 글을 그대로 둔다. "라면 만드는 회사는?" 같은 질문이 오면 Agent가 낱말로 찾고(`search_business`), 매출 비중 표를 읽어(`get_business`) 주력인 회사와 언급만 있는 회사를 나눠 답한다
- **제품**은 매출 비중의 합이 100에 가까운 표만 읽는다. 제품 절이 있는 2,659곳 가운데 1,793곳을 읽었고 866곳은 읽지 못했다. 읽지 못한 회사는 화면에 그렇게 표시한다
- 같은 제품을 회사마다 다르게 적어서("분리막", "LiBS", "2차전지 분리막"), 표에 적힌 이름은 그대로 두고 이름을 세 층으로 따로 붙였다: **분야 > 제품군 > 제품**.
  제품군은 닫힌 목록이다(23개 분야, 159개. `product_families.py`). 나누는 기준은 "같은 제품군의 회사끼리 경쟁하거나 대체할 수 있는가"라서,
  반도체를 만드는 회사(메모리 반도체, 시스템 반도체)와 반도체 장비·소재 회사는 다른 제품군이다
- 이름은 줄 하나가 아니라 **회사의 표 전체와 사업 개요를 같이 보고** 붙였다. 상표("토망고")나 뭉뚱그린 칸("제품")만 봐서는 무엇인지 알 수 없기 때문이다.
  회사별로 9,043줄을 Claude Opus가 읽고 붙였다(이 저장소를 만든 대화 안에서 했고, 같은 안내문과 목록으로 다시 할 수 있다: `product_naming.py`).
  제품이라 할 것이 없는 줄(임대, 배당, 연결조정, 지역으로 나눈 줄 등) 1,954줄은 비워 두었고, 짐작이 섞인 1,511줄에는 표시를 남겼다
- 처음에는 줄 하나씩 Claude Haiku API로 붙였다. 무작위 100줄을 다시 보니 맞음 82, 애매함 10, 비움 4, 틀림 4였다. 지금 방식으로 같은 100줄을 다시 보면
  틀림은 찾지 못했고 애매함이 5줄쯤 남는다. 판정은 원문을 다시 열지 않고 표의 글과 개요만 보고 한 것이며, 사람이 전부 확인한 것은 아니다
- 그래프에서는 `기업 → 제품 → 제품군`으로 이어진다. 두 곳 이상이 함께 파는 제품 1,013가지와 제품군 159개가 점이 되고, 선의 굵기는 매출 비중이다

**없는 것**: 분기보고서, 반기보고서의 지분·계열 표(반기보고서는 사업 내용만 읽었다), 최대주주와 특수관계인이 아닌 주주, 주요 고객(사업보고서 본문 서술), 합병·분할, 뉴스, 주가.

## 설계에서 신경 쓴 곳

**날짜를 셋으로 나눈다.** 관계 한 줄마다 기준일(사실이 성립한 날), 공개일(공시된 날), 무효일(정정·해지·철회로 바뀐 날)을 따로 둔다.
공급계약 공시의 절반 이상이 정정 공시라서, 날짜가 하나면 과거 시점을 조회할 때 나중에 고친 값이 섞인다.
분기마다 시점을 옮겨 조회한 선 59,130개 중 그 시점보다 나중에 공개된 것은 0개였다 (`check_equity`).

**줄을 지우지 않는다.** 추출기를 고쳐 다시 돌리면 같은 줄은 두고, 달라진 줄에는 내린 날짜만 찍고, 새 줄을 더한다 (`loader.sync`).
추출기를 고칠 때마다 바뀐 줄 수가 나오므로, 고친 것이 다른 곳을 망가뜨렸는지 바로 보인다.

**모든 줄에 근거가 있다.** 접수번호, 누가 밝혔는지(주체의 공시 / 상대의 공시 / 양쪽), 이름을 어떤 근거로 연결했는지(법인등록번호 / 이름 일치)를 남긴다.
상대를 원장에서 못 찾아도 줄을 버리지 않고 공시에 적힌 이름 그대로 둔다.

**정답 없이 검산한다.**

| 검사 | 결과 |
|---|---|
| 공급계약: 계약금액 ÷ 최근 매출액이 공시에 적힌 비율과 맞는가 | 11,739 / 11,853 |
| 취득·처분: 금액 ÷ 자기자본이 적힌 비율과 맞는가 | 2,901 / 2,923 |
| 계열: 읽은 줄 수가 표에 적힌 회사 수와 같은가 | 6,301 / 6,438 |
| 계열: 공정위 지정 명단(이듬해 5월)과 겹치는 정도 | 정밀도 94.9%, 재현율 94.6% |
| 지분: 가진 쪽 공시와 내준 쪽 공시의 지분율이 서로 맞는가 | 1,939 / 2,307 |

아래 두 줄은 추출 정확도가 아니라 두 자료가 서로 맞는 정도다. 공정위 명단은 시점이 다르고(12월 보고서, 5월 명단), 지분율은 같은 날짜에도 두 회사가 다르게 적는 경우가 많다.
비율이 맞지 않는 줄은 원문에 적힌 대로 넣고 표시해 둔다. 확인한 것들은 원문의 오기였다(쉼표 자리에 마침표 등).

## Agent

Agent는 SQL을 쓰지 않고 조회 함수 열한 가지만 부른다 (`agent_tools.py`).
조회 시점은 필수이고, 기업은 `find_company`가 준 번호로만 가리키고, 결과가 비면 수집 범위를 같이 돌려준다.
답에 적힌 접수번호가 실제 도구 결과에 있었는지 끝에서 확인한다.

질문은 두 갈래다. **관계를 묻는 질문**("현대모비스의 최대주주는?")은 관계 표를 조회한다.
**이슈나 주제로 회사를 찾는 질문**("화장품을 대신 만들어 주는 회사는?")은 업종 분류로 답하지 않고, 제품 표에서 제품군이나 제품 이름으로 찾거나(`find_by_product`, 매출 비중이 바로 나온다. 제품군 목록은 도구 설명에 실려 있어 Agent가 질문의 뜻에 맞는 것을 고른다) 사업 내용의 글에서 낱말로 찾은 뒤 매출 비중으로 주력인지 확인한다.
제품 표를 읽지 못한 회사는 제품 조회에 나오지 않으므로(예: "라면"으로 찾으면 0곳이다) 글 검색을 함께 쓰게 했다.
수혜를 볼지, 주가가 오를지는 말하지 않고 "보고서에 이 사업을 한다고 적혀 있다"까지만 말한다.

## 평가

**평가 2판** ([eval/v2/results.md](eval/v2/results.md)): 공시 원문에서 직접 쓴 149문항. 한 칸을 읽으면 끝나는 질문은 빼고, 정정 사이의 시점을 가리거나 여러 공시를 견주어야 답할 수 있는 질문만 썼다. 도구를 다 만든 뒤 한 번 돌렸다.

| 판정 | Agent 149문항 | 같은 100문항: Agent (claude-haiku-5-5) | 같은 100문항: 웹 검색만 쓴 Claude (claude-opus-5-5) |
|---|---|---|---|
| **정답 또는 부분 정답** | **134 (90%)** | **89** | **70** |
| 정답 (물은 값을 모두 맞힘) | 79 | 50 | 31 |
| 부분 정답 (일부만 맞힘, 틀린 사실 없음) | 55 | 39 | 39 |
| 답하지 못함 | 5 | 4 | 15 |
| 틀린 사실을 답함 | 10 | 7 | 15 |
| 문항당 시간 (중앙값) | 8.8초 | 9.1초 | 108초 |
| 문항당 토큰 (중앙값) | 약 23,000 | 약 23,400 | 약 74,600 |

- 문항은 추출기와 DB를 보지 않고 원자료만으로 썼고, 쓴 쪽과 다른 검토자가 다시 확인했고, 채점은 어느 쪽 답인지 모르는 채점자가 했다. 모두 Claude가 했고 사람이 원문을 직접 본 것은 아니다
- 웹 검색과는 종류마다 5~7문항씩 100문항을 견주었다. 시간(약 12배)과 토큰(약 3배)의 차이는 분명하다. 웹 검색은 공시 원문을 한 번도 열지 못했다(페이지 읽기 592번 중 337번 실패)
- 부분 정답의 대부분은 DB에 있는 값을 조회 도구가 내주지 않아 생겼다(자기자본 대비 비율 10문항, 취득 예정일자 7문항). 위 표는 고치기 전 점수다
- 그 결함을 고치고 같은 149문항을 다시 돌리면 정답 118 (79%), 부분 정답까지 138 (93%), 틀린 사실 10이다. 문항을 알고 고친 것이라 처음 점수와 따로 적는다
- 문항, 정답, 두 쪽의 답과 판정 사유는 사이트의 "평가 문항"에서 모두 볼 수 있다

아래 평가는 모두 관계를 묻는 질문이다. **이슈형 질문의 답은 아직 측정하지 않았다.** 몇 개를 읽어 본 것뿐이라 점수가 없다.

**평가 1판(봉인 시험)** ([eval/sealed/results.md](eval/sealed/results.md)): 기업과 공시를 고정된 씨앗으로 무작위 추출한 30문항을, 도구를 다 만든 뒤 한 번 돌렸다.

| 판정 | 문항 수 |
|---|---|
| 정답 | 24 |
| 부분 정답 | 4 |
| 답하지 못함 | 2 |
| 틀린 사실을 답함 | 0 |

- 정답률 80% (95% 구간 63~91%). 30문항이라 구간이 넓다. 지어낸 접수번호는 0건
- 정답은 추출기를 거치지 않은 원자료(공시 원문, 공시 목록, API 응답, 사업보고서 본문)와 Claude가 세 번 대조했고, 3차는 별개의 검토자에게 맡겼다. 사람이 원문을 직접 본 것은 아니다
- 시험이 DB의 결함을 찾았다: 해지된 계약이 유효한 것으로 조회되던 문제(94줄), 이름을 고친 정정 공시가 이어지지 않던 문제, API가 출자 표의 일부만 돌려주는 문제. 고쳤지만 점수는 고치기 전 것으로 둔다

연습 문항과 모델 비교, 기준선의 원자료는 `eval/`에 있다.

## 실행

필요한 것: Python 3.12, Node, Docker. OpenDART와 공공데이터포털(공정위 기업집단) API 키는 무료로 발급받는다.

```bash
cp .env.example .env            # 비밀번호를 채운다. 키는 사용자 환경 변수 DART_API_KEY, DATA_GO_KR_API_KEY 에 둔다
docker compose up -d            # MySQL
python -m venv .venv && .venv/Scripts/pip install -r requirements-dev.txt
```

수집과 추출 (OpenDART는 하루 2만 건 제한이 있어 며칠에 나눠 돈다. 한도에 닿으면 멈추고, 같은 명령으로 이어 받는다):

```bash
python -m company_graph.load_companies
python -m company_graph.extract_equity --all
python -m company_graph.extract_affiliates
python -m company_graph.extract_equity --all      # 계열회사 표로 이름 연결을 다시 맞춘다
python -m company_graph.extract_invest_detail
python -m company_graph.extract_supply --all
python -m company_graph.extract_stakes --all
python -m company_graph.extract_business annual 2025     # 사업 내용 (사업보고서)
python -m company_graph.extract_business half 2026       # 사업 내용 (반기보고서)
python -m company_graph.extract_products                 # 제품 표. DART를 다시 부르지 않는다
python -m company_graph.product_naming export            # 이름 붙일 일감과 안내문을 data/product_naming/ 에 쓴다
```

## 알려진 한계

- 원장에 없는 상대(비상장사, 해외 법인)는 이름만 있어 그래프의 점이 되지 않는다
- 해지 공시 중 일부는 같은 날 같은 상대와 맺은 계약이 여럿이라 어느 계약의 해지인지 잇지 못했다
- 출자 상세표를 표준과 다른 칸 구성으로 적은 보고서 34건(대부분 한 은행)은 읽지 않았다
- 계열회사를 요약 표에만 적거나 해외 계열사를 다른 형식의 표에 적은 회사는 계열 줄이 없다
- 제품 표는 866곳을 읽지 못했다(매출 비중의 합이 100이 되지 않는 표, 비중 칸이 없는 표). 금융업은 제품 표 자체가 없다
- 제품 이름과 제품군은 모델이 붙였고 사람이 전부 확인하지 않았다. 표의 한 줄에 여러 제품이 적혀 있으면 그 줄의 비중이 제품마다 그대로 붙는다(줄 안의 비중은 보고서에 없다)
- 매수·매도 판단은 답하지 않는다
