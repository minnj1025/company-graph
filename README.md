# Corpath · 공시 기반 기업 관계 그래프

금융감독원 전자공시(DART)에서 **기업과 기업의 관계**(지분, 계열, 공급계약)와 **기업이 무엇을 하는지**(사업 내용, 제품), 재무·주주·자본 결정을 뽑아 시점이 붙은 DB로 만들고, 화면과 Agent로 조회한다.
매일 아침에는 Agent가 전날 상장사 뉴스에서 핵심을 스스로 골라, 뉴스의 주인공에서 공시로 이어진 회사들을 근거 공시와 함께 정리한다(뉴스 분석).
"현대모비스에 납품 계약을 공시한 회사는?", "이 계약은 작년 말 시점에 어떻게 알려져 있었나?", "이 수주 뉴스는 어느 회사들과 공시로 이어지나?" 같은 질문에 근거 공시와 함께 답하는 것이 목표다.

개인 프로젝트다. 사이트는 https://company-graph-nu.vercel.app 이다. 설계와 진행 기록은 [DESIGN.md](DESIGN.md), 참고한 문헌·사례는 [docs/landscape.md](docs/landscape.md)에 있다.

## 사이트에서 하는 것

| 화면 | 하는 것 |
|---|---|
| 탐색 | 관계를 3D 그래프로 그린다. 조회 시점을 옮기면 그날까지 공시된 관계만 그린다. 아래 입력 칸에 기업 이름을 넣으면 바로 찾고, 문장을 넣으면 Agent가 답한다. Agent는 답에 나오는 기업을 그래프에 띄우고 시각화 카드(15종)를 고른다 |
| 뉴스 분석 | 매일 아침 Agent가 고른 뉴스 10건의 분석. 뉴스에서 주인공을 거쳐 공시로 이어진 회사(회사마다 이어지는 까닭 한 줄과 접수번호), 뉴스 뒤 주인공이 낸 공시, 뉴스 뒤 주가 변화(누적 %). 화면에서 제목을 넣어 직접 돌릴 수도 있다 |
| 이슈 종목 | 그날 함께 크게 움직인 종목을 같은 제품이나 직접 이어진 관계로 묶는다. 뚜렷한 묶음에는 그날 기사가 전한 배경을 한 줄로 붙인다 |
| 내 종목 | 방문자가 고른 종목의 등락률, 보유 비중, 최근 공시, 연관 급등·급락에 든 날. 목록은 브라우저에만 저장한다 |
| 데이터와 검증 · 평가 문항 | 검산 결과, 평가에 쓴 문항과 정답, 답과 판정 사유 |

다른 사람의 Claude(또는 다른 Agent)가 같은 조회 도구를 쓰도록 MCP 입구 `/api/mcp` 를 열어 두었다(`mcp_server.py`, 도구 16개). 그쪽 모델과 그쪽 비용으로 돈다. 주가 도구는 내놓지 않는다(아래 KRX 조건).

- 이름은 줄 하나가 아니라 회사의 표 전체와 사업 개요를 같이 보고 Claude Opus가 붙였다(`product_naming.py`). 다른 검토자가 이름이 붙은 줄에서 무작위 200줄을 다시 보니 맞음 189, 제품군 어긋남 6, 이름 어긋남 2, 판단 불가 3, 틀림 0이었다. 원문을 다시 열지 않고 표의 글과 개요만 보고 한 판정이며, 사람이 전부 확인한 것은 아니다

## 설계에서 신경 쓴 곳

**날짜를 셋으로 나눈다.** 관계 한 줄마다 기준일(사실이 성립한 날), 공개일(공시된 날), 무효일(정정·해지·철회로 바뀐 날)을 따로 둔다.
공급계약 공시의 절반 이상이 정정 공시라서, 날짜가 하나면 과거 시점을 조회할 때 나중에 고친 값이 섞인다.
분기마다 시점을 옮겨 조회한 선 59,130개 중 그 시점보다 나중에 공개된 것은 0개였다 (`check_equity`). 이것은 줄 기준이다. 뉴스 분석을 시험하다가, 조회 시점에 유효했던 계약에 그 뒤에 정정·해지·철회된 날짜(`superseded_on`)가 칸 하나로 새는 것을 찾아 고쳤다.

**줄을 지우지 않는다.** 추출기를 고쳐 다시 돌리면 같은 줄은 두고, 달라진 줄에는 내린 날짜만 찍고, 새 줄을 더한다 (`loader.sync`).
추출기를 고칠 때마다 바뀐 줄 수가 나오므로, 고친 것이 다른 곳을 망가뜨렸는지 바로 보인다.

**모든 줄에 근거가 있다.** 접수번호, 누가 밝혔는지(주체의 공시 / 상대의 공시 / 양쪽), 이름을 어떤 근거로 연결했는지(법인등록번호 / 이름 일치)를 남긴다.
상대를 원장에서 못 찾아도 줄을 버리지 않고 공시에 적힌 이름 그대로 둔다.

**정답 없이 검산한다.**

| 검사 | 결과 |
|---|---|
| 공급계약: 계약금액 ÷ 최근 매출액이 공시에 적힌 비율과 맞는가 | 11,739 / 11,853 |
| 취득·처분: 금액 ÷ 자기자본이 적힌 비율과 맞는가 | 2,901 / 2,923 |
| 계열: 읽은 줄 수가 표에 적힌 회사 수와 같은가 | 6,301 / 6,438 |
| 계열: 공정위 지정 명단(이듬해 5월)과 겹치는 정도 | 정밀도 94.9%, 재현율 94.6% |
| 지분: 가진 쪽 공시와 내준 쪽 공시의 지분율이 서로 맞는가 | 1,939 / 2,307 |
| 재무: 평가 7판 정답 37개를 도구의 값과 견줌 (`eval.v7.data_check`) | 37 / 37 |
| 사채: 가액 × 전환 주식 수 ≈ 권면총액 (`capital check`) | 1,386 / 1,388 |

공정위 명단과 지분율 두 줄은 추출 정확도가 아니라 두 자료가 서로 맞는 정도다. 비율이 맞지 않는 줄은 원문에 적힌 대로 넣고 표시해 둔다. 확인한 것들은 원문의 오기였다(쉼표 자리에 마침표 등).

## Agent

Agent(claude-haiku-5-5)는 SQL을 쓰지 않고 조회 도구 18개와 화면 도구 하나(`show_on_graph`)만 부른다 (`agent_tools.py`, 평가 2판 당시는 조회 도구 13개).
조회 시점은 필수이고, 기업은 `find_company`가 준 번호로만 가리키고, 결과가 비면 수집 범위를 같이 돌려준다(`get_coverage`). 답에 적힌 접수번호가 실제 도구 결과에 있었는지 끝에서 확인한다.

- **관계를 묻는 질문**("현대모비스의 최대주주는?")은 관계 표를 조회한다. **주제로 회사를 찾는 질문**("화장품을 대신 만들어 주는 회사는?")은 업종 분류로 답하지 않고 제품 표(`find_by_product`)나 사업 내용의 글에서 찾은 뒤 매출 비중으로 주력인지 확인한다
- 시각화 카드는 Agent가 종류와 대상만 고르고 숫자는 서버가 DB에서 채운다(`views.py`). 모델이 숫자를 옮기다 틀릴 자리를 없애려는 것이다
- 원인이나 평가를 묻는 질문에는 원인을 판단하지 않고 따져 볼 사실을 근거와 함께 모은다. 매수·매도 판단과 전망은 하지 않는다
- 사이트에서는 하루 질문 수에 한도가 있다(방문자 한 명, 전체)

## 뉴스 분석

`news_agent.py` 는 뉴스 한 건을 받아 할 일이 정해진 Agent다. 주인공 회사와 뉴스가 닿는 제품·사업을 찾고, 공급계약 상대, 지분·계열, 같은 제품을 파는 회사를 조회해 분석을 낸다. 어느 도구를 몇 번 부를지는 모델이 정하고, 첫 응답에 조회 계획을 먼저 낸다.

- **조회 시점은 뉴스 전날이다.** 뉴스 뒤에 나온 공시는 보지 않는다. 나중에 결과와 견줄 때 미래를 섞지 않으려고
- 관련 회사마다 근거 공시의 접수번호를 붙이게 하고, 그 접수번호와 회사가 실제 조회 결과에 있었는지 코드가 확인한다. 어긋나면 한 번 고치게 하고, 남은 것은 빼고 뺐다고 적는다. 매일 분석과 화면에서는 분석에 적힌 금액·비율·날짜도 조회 결과에 있는지 검사한다
- 기사는 제목만 쓴다. 본문은 저장소와 DB에 넣지 않고 분석에 기사 문장을 옮기지 않는다

**매일 분석** (`daily_memos.py`): 시가총액 상위 200곳의 전날 Google 뉴스 제목을 모아, 평가 12판과 같은 지시문으로 주인공·분야·중요도를 매긴다. 주인공이 그 회사이고 산업 뉴스이며 중요도 0.7 이상인 것을 중요도 순으로 10건 분석한다. 한 회사에서 한 건이고, 같은 사건(같은 종류에 금액이 2% 안)은 여러 회사에서 잡혀도, 앞선 7일 안에 이미 분석했어도 한 번만 한다. 첫 운영 실행(2026-11-06 뉴스)은 제목 1,368건에서 10건을 분석했고 $0.1404 들었다.

**뉴스 뒤에 확인한 것**은 분석 뒤에 코드가 붙인다. 모델은 이 단계에 관여하지 않는다.
- 뉴스 뒤 공시 (`memo_followups.py`): 조회 시점 다음 날부터 60일 안에 주인공이 낸 공급계약·해지, 지분 취득·처분 결정, 증자·사채·자기주식 결정. 뉴스 제목의 금액과 3% 안쪽이면 같다고 표시한다. 같은 일인지는 원문으로 확인해야 한다
- 집계 (`/api/memo-scoreboard`): 뉴스 종류마다 분석 수, 제목에 금액이 있는 수, 뒤에 그 종류의 공시를 낸 수, 금액이 같은 수. 확인해 줄 공시를 모으지 않는 종류(투자·증설, 실적)는 세지 않는다. Agent의 판단을 채점한 것이 아니다. 아직 며칠 치뿐이라 이 수를 성과로 쓰지 않는다
- 같은 회사의 다른 분석: 분석 한 건 아래에 그 주인공의 다른 날 분석을 잇는다(`/api/memos/{번호}` 의 `others`)
- 뉴스 뒤 주가 (`memo_prices.py`): 뉴스 전 거래일 종가를 0으로 둔 누적 %. 견줄 기준은 보통 종목(수익률 중앙값)과 시장 전체(시가총액 가중) 둘이다. 사후 기록일 뿐이며, 아래 평가 12판에서 공시로 고른 종목이 키워드 방식보다 낫지 않았다는 결과를 화면에 같이 적는다

## 평가

문항 작성, 채점, 답 생성은 모두 Claude가 했다. 작성자와 채점자는 서로 다른 하위 작업이고, 채점은 가능한 한 어느 쪽 답인지 가린 채로 했다. 사람이 원문을 직접 본 것은 아니다. 문항을 보고 고친 뒤의 점수는 처음 점수와 따로 적는다.

**평가 2판** ([eval/v2/results.md](eval/v2/results.md)): 공시 원문에서 직접 쓴 149문항. 한 칸을 읽으면 끝나는 질문은 빼고, 정정 사이의 시점을 가리거나 여러 공시를 견주어야 답할 수 있는 질문만 썼다. 문항은 추출기와 DB를 보지 않고 원자료만으로 썼다.

| 판정 | Agent 처음 (149문항) | 같은 100문항: Agent 처음 (claude-haiku-5-5) | 같은 100문항: 웹 검색만 쓴 Claude (claude-opus-5-5) |
|---|---|---|---|
| **정답 또는 부분 정답** | **134 (90%)** | **89** | **70** |
| 정답 (물은 값을 모두 맞힘) | 79 | 50 | 31 |
| 부분 정답 (일부만 맞힘, 틀린 사실 없음) | 55 | 39 | 39 |
| 답하지 못함 | 5 | 4 | 15 |
| 틀린 사실을 답함 | 10 | 7 | 15 |
| 문항당 시간 (중앙값) | 8.8초 | 9.1초 | 108초 |

- 웹 검색은 공시 원문을 한 번도 열지 못했다(페이지 읽기 592번 중 337번 실패)
- 부분 정답의 대부분은 DB에 있는 값을 조회 도구가 내주지 않아 생겼다. 그 결함을 고치고 도구를 더한 뒤(2026-10-11) 같은 149문항에서 정답 124, 부분 정답 16, 답하지 못함 2, 틀린 사실 7이다(문항당 약 $0.0041). 같은 구성에 가장 큰 모델(Opus)을 쓰면 정답 127, 틀린 사실 5이고 문항당 약 $0.142다. 모두 문항을 알고 고친 뒤의 점수다

**평가 1판(봉인 시험)** ([eval/sealed/results.md](eval/sealed/results.md)): 고정된 씨앗으로 무작위 추출한 30문항을 도구를 다 만든 뒤 한 번 돌렸다. 정답 24, 부분 정답 4, 답하지 못함 2, 틀린 사실 0. 지어낸 접수번호 0건. 이 시험이 해지된 계약이 유효한 것으로 조회되던 문제(94줄) 등을 찾았고, 점수는 고치기 전 것으로 둔다.

## 실행

필요한 것: Python 3.12, Node, Docker. OpenDART와 공공데이터포털(공정위 기업집단) API 키는 무료로 발급받는다. 시세는 KRX OPEN API 키, Agent와 뉴스 분석은 Anthropic API 키가 필요하다. 키는 모두 환경 변수에 둔다.

```bash
cp .env.example .env            # 비밀번호를 채운다. 키는 사용자 환경 변수 DART_API_KEY, DATA_GO_KR_API_KEY 등에 둔다
docker compose up -d            # MySQL
python -m venv .venv && .venv/Scripts/pip install -r requirements-dev.txt
```

수집과 추출 (OpenDART는 하루 2만 건 제한이 있어 며칠에 나눠 돈다. 한도에 닿으면 멈추고, 같은 명령으로 이어 받는다):

```bash
python -m company_graph.load_companies
python -m company_graph.display_names --apply
python -m company_graph.extract_equity --all
python -m company_graph.extract_affiliates
python -m company_graph.extract_equity --all      # 계열회사 표로 이름 연결을 다시 맞춘다
python -m company_graph.extract_invest_detail
python -m company_graph.extract_supply --all
python -m company_graph.extract_stakes --all
python -m company_graph.extract_business annual 2025     # 사업 내용 (사업보고서)
python -m company_graph.extract_business half 2026       # 사업 내용 (반기보고서)
python -m company_graph.extract_products                 # 제품 표. DART를 다시 부르지 않는다
python -m company_graph.financials load
python -m company_graph.holdings load
python -m company_graph.capital load
python -m company_graph.prices                           # KRX 시세 (KRX_API_KEY)
```

검산, 화면, Agent:

```bash
python -m pytest tests
python -m company_graph.check_equity
python -m company_graph.check_affiliates
python -m company_graph.financials check
python -m company_graph.capital check
python -m uvicorn company_graph.api:app --port 8000
```

DART 원문, 기사, DB는 저장소에 넣지 않았다(`data/`). 공시 원문의 재배포 조건을 확인하지 않았기 때문이다.

## 알려진 한계

- **없는 것**: 분기보고서의 지분·계열 표, 최대주주와 특수관계인이 아닌 주주(5% 보고로 일부만), 주요 고객(사업보고서 본문 서술), 합병·분할, 거래소 공시(자기주식 소각결정, 잠정실적, 중재, 영업정지 등)
- 원장에 없는 상대(비상장사, 해외 법인)는 이름만 있어 그래프의 점이 되지 않는다
- 해지 공시 중 일부는 같은 날 같은 상대와 맺은 계약이 여럿이라 어느 계약의 해지인지 잇지 못했다
- 계열회사를 요약 표에만 적거나 해외 계열사를 다른 형식의 표에 적은 회사는 계열 줄이 없다
- 제품 표를 읽지 못한 회사가 있다(매출 비중의 합이 100이 되지 않는 표, 비중 칸이 없는 표). 금융업은 제품 표 자체가 없다
- 제품 이름과 제품군은 모델이 붙였고 사람이 전부 확인하지 않았다. 표의 한 줄에 여러 제품이 적혀 있으면 그 줄의 비중이 제품마다 그대로 붙는다
- 연관 급등·급락의 연결 고리는 공통점이지 원인이 아니다. 원인은 기사가 전한 것만 적고, 찾지 못하면 찾지 못했다고 둔다
- 시세는 KRX 이용약관(비상업, 제3자 제공 금지)에 따라 가공한 값만 낸다
- 매수·매도 판단은 답하지 않는다
