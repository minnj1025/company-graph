# 평가 4판 — 구조를 바꾸기 전에 정한 것 (2026-10-12)

결과를 보기 전에 적는다. 문항(X1~X5, 40개)은 구조를 고치는 쪽과 다른 작성자가 원자료만 보고 썼고, 고치는 쪽은 구현이 끝날 때까지 문항을 열지 않았다.

## 견줄 구성

Agent의 뼈대는 그대로 단일 도구 호출 루프다. 환경 변수로 켜고 끈다.

| 구성 | 켜는 것 | 뜻 |
|---|---|---|
| A 기준선 | 없음 | 지금 서비스와 같은 구조 (도구 13개) |
| B 합성 도구 | `ASK_COMPOSITE=1` | 두 보고서 대조(compare_reports), 주주 명단 변동(holder_changes)을 도구 하나로 |
| C 합성 도구 + 검증 | `ASK_COMPOSITE=1 ASK_VERIFY=1` | 답의 숫자·날짜·접수번호를 조회 결과와 코드로 대조하고, 어긋나면 한 번 다시 쓰게 함 |

모델은 세 구성 모두 `claude-haiku-5-5`. 데이터는 같은 DB(추출기 equity-5)다.

## 문항

- 새 문항 40개(eval/v4/gold): 처음 보는 문항. 구조를 바꾸기 전에 썼고 쓴 뒤에는 고치지 않는다
- 기존 149문항(eval/v2/gold): 나빠지지 않았는지 보는 데 쓴다. 이 문항들은 이미 보고 고친 적이 있으므로 좋아진 것은 근거로 삼지 않는다

## 채택 기준

구성 B와 C를 각각 A와 견준다. 아래를 모두 채워야 서비스에 반영한다.

1. 새 40문항에서 정답 수가 4문항 이상 늘 것 (10%p)
2. 새 40문항과 기존 149문항 어디에서도 틀린 사실을 답한 문항이 늘지 않을 것
3. 기존 149문항에서 정답 수가 3문항 넘게 줄지 않을 것
4. 문항당 비용(토큰에 단가를 곱한 값)의 중앙값이 A의 1.5배를 넘지 않을 것

C는 B와도 견준다: 검증을 더해 틀린 사실이 줄지 않으면 검증은 반영하지 않는다(비용만 늘기 때문).

## 미리 알고 있는 것 (결과를 보기 전)

- 검증기를 기존 149개 답에 대어 보면(다시 돌리지 않고 기록된 도구 호출을 재실행), 정답 124문항 가운데 8문항에서 헛발동했고 오답 7문항 가운데 1문항만 걸렸다. 기존 오답은 값을 잘못 옮긴 것보다 빠뜨린 것이 많아서다. 검증이 정확도를 올리지 못할 수 있다
- 합성 도구는 2판에서 두 모델이 함께 틀린 문항(T14-02, T14-06, T11-07)의 경우에서 필요한 값을 내주는 것을 확인했다. 이 세 문항은 보고 만든 것이므로 근거로 삼지 않는다

## 채점

2판과 같은 기준(eval/v2/GRADING.md). 세 구성의 답을 섞어 어느 구성의 답인지 가린 채 채점한다. 채점은 Claude가 한다.
